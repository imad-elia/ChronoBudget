## Found by the user testing the web build in desktop Chrome (2026-08-30)

Seven issues reported after running `npx expo start` and testing in Chrome (not iOS/Android). All fixed same session; user has not yet re-tested in the browser (fixed per explicit instruction not to browser-test myself this round).

### Fixed

- **CSV export was hardcoded to English regardless of the selected language.** `app/(tabs)/history.tsx`'s `handleExport` built the header row (`'Date,Time,Category,Subcategory,Note,Amount'`) and the `Category` cell (raw `'needs'|'wants'|'savings'`) as literal English, and the native share-sheet dialog title was a literal string too — none of it used `t()` even though the same file already calls `t()` elsewhere. Fixed: header and category cell now go through new `csv.header.*` keys and the existing `category.*` keys; share dialog title uses a new `history.exportDialogTitle` key. Date/time cells stay in a fixed ISO-ish format (`en-CA`/`en-US`-formatted, unchanged) deliberately — `lib/csv.ts:parseCsv` reconstructs the timestamp from those cells via `new Date(\`${date}T${time}:00\`)`, which needs an unambiguous format regardless of language, not a locale-formatted one. To keep a French export re-importable, `lib/csv.ts` now also recognizes the French header row and French category labels (`Besoins/Envies/Épargne`) by importing `constants/i18n/en.ts`/`fr.ts` directly and building a small reverse lookup, instead of matching only the raw English enum. New test: `lib/__tests__/csv.test.ts` round-trips a French-language export.
- **Recent-list dates on the Dashboard were hardcoded to `en-US`.** `app/(tabs)/index.tsx`'s `TransactionRow` called `toLocaleDateString('en-US', {...})` directly instead of reading the store's `locale`. `lib/format.ts`'s `formatDate` already exists and does this correctly elsewhere but wasn't reusable here as-is (its `dateStyle: 'medium'` has no time component, and this row needs date+time). Fixed by reading `locale` via a reactive `useBudgetStore((s) => s.locale)` selector (not `.getState()`, so the row re-renders on a live language switch) and passing it into the same `toLocaleDateString` call.
- **Over-limit category cards showed a percentage/bar (e.g. "136%") instead of plain spent-vs-limit numbers.** `components/BentoCard.tsx` always rendered `<ProgressBar>` (bar + uncapped percentage + OVER badge) once a limit was set, even past 100%. Product call: past 100%, absolute numbers communicate the overspend better than a ratio. Fixed by branching in `BentoCard.tsx`: when `amount / limit > 1`, render the OVER badge plus a plain `"$X / $Y"` text line instead of `<ProgressBar>`; at or under the limit, unchanged. `components/ProgressBar.tsx` itself is untouched (still used as-is by `GoalsModal.tsx` for goal progress, not part of this report). `components/__tests__/BentoCard.test.tsx` updated to match.
- **Large amounts truncated with "…" in BentoCard on web** (e.g. "$1,001,301.01" → "$1,001,…"). Cause: `adjustsFontSizeToFit` is iOS-only and silently does nothing on React Native Web, so the 32px `displayMedium` font never shrank and `numberOfLines={1}` clipped the overflow. Fixed with a small cross-platform `amountFontSize(formatted)` helper in `BentoCard.tsx` that picks a smaller font size (32/26/21px) by the formatted string's length, computed in JS so it works identically on web and native.
- **Trends' compact currency lost its thousands separator past 1,000** (e.g. "$1,001,249.01" showed as "$1001.2k" instead of "$1,001.2K"). `lib/format.ts:formatCompactCurrency` divided by 1000 and appended `k` without re-grouping the quotient — the file already has a `grouped()` helper used correctly by `formatCurrency`/`formatNumber`, just not applied here. Fixed by reusing `grouped()` on the divided value and capitalizing to `K` (matches the user's expected output — no new "M" tier was requested or needed, since the reported example is still meant to read as thousands). `app/(tabs)/trends.tsx` needed no changes, since it already imports this same function. New test in `lib/__tests__/format.test.ts` covers the >1,000,000 grouping case.
- **A newly-typed custom subcategory vanished after "Add" — didn't reappear as a chip for the next entry.** `components/ExpenseInput.tsx`'s subcategory chip row (`subcats`) was pulled straight from the static `constants/subcategories.ts` list, which never changes at runtime; `resetFields()` clears the typed custom text after every submit, and nothing wrote the new value anywhere the chip row could read it back from (it was correctly saved on the transaction row itself, just not remembered as a future chip option). Fixed following the same cached-from-SQLite pattern already used for `learnedKeywords`: new `customSubcategories: Record<Category, string[]>` state in `store/useBudgetStore.ts`, persisted as one JSON blob via the existing generic `getSetting`/`setSetting` key-value helpers (`db/database.ts`, no schema change needed), loaded at app-mount alongside the other init loaders in `app/(tabs)/index.tsx`. `ExpenseInput.tsx`'s `subcats` now concatenates the static list with the per-category custom list, and calls `addCustomSubcategory()` on a successful custom-value submit. New tests in `store/__tests__/useBudgetStore.test.ts`. Custom subcategories remain untranslated by design (unchanged, matches `DET-02`'s "stored verbatim" expectation).
- **"What does DET-04 check?"** — not a code issue, a manual test-case lookup. `DET-04` (P0) is from the "ChronoBudget Release Test Plan" artifact (published 2026-08-29, not stored in the repo — `claude.ai/code/artifact/713ca170-f7ad-4a6c-866e-8a7458554617`): *"Account tagging debits the account atomically."* Precondition: Checking = 1200. Steps: add a 50 transaction tagged to Checking, check the accounts row/modal. Expected: Checking = 1150 immediately, and the category total also increases by 50.

### Known extension (not part of this report, noted while fixing #6)

- `components/EditTransactionModal.tsx` and `components/RecurringModal.tsx` each have their own separate, similarly-static subcategory chip list, so a custom value added in one of those flows wouldn't pick up the new `customSubcategories` store field either. Not reported by the user and not changed here — the bug report was specifically about the main add-expense flow (`ExpenseInput.tsx`). Worth applying the same fix there if it comes up again.

## Found while automating the test plan (2026-08-29, later session)

See [[2026-08-29c-session]] and [[testing-strategy]].

### Fixed

- **The sqlite test mock never ran a real transaction.** `__mocks__/expo-sqlite.ts` implemented `withTransactionAsync` as `await callback()` — no BEGIN, no COMMIT, no ROLLBACK. Every existing assertion about money moving "atomically" (account debits, goal progress, recurring catch-up) was really asserting the statements ran in order; a mid-transaction failure would have left partial writes with nothing to catch it. Fixed to issue real SQL with ROLLBACK on throw. Nothing broke once it was real — the behaviour was correct, it just had no coverage. New regression test: `insertTransfer` debits the source account before the transfer row insert fails on its foreign key, so without a real ROLLBACK the debit survives and money vanishes.
- **Jest was running the stale worktree's mock, not the project's.** jest-haste-map found two manual mocks named `expo-sqlite` — `__mocks__/expo-sqlite.ts` and a copy under `.claude/worktrees/exciting-bose-b67c07/` — and resolved the worktree's. This meant the entire DB suite had been exercising a mock nobody was editing, and it is why the transaction fix above appeared not to work at first. Fixed with `modulePathIgnorePatterns` in the Jest config rather than by deleting the worktree, which is yours to remove. This also cleared the long-standing parallel-worker timeouts: the suite went from six failing suites in 24s to clean in 7s, so `npm test` is trustworthy again without `--runInBand`.
- **A seventh frozen-label instance, found by the new static check on its first run.** `RecurringModal.tsx`'s `FREQUENCY_LABEL` computed `t()` at module scope, freezing the Weekly/Monthly/Yearly labels in the recurring-rule list to whichever locale was active at import. Same bug class as the six before it, and the correct keys-only pattern (`FREQUENCIES` with `labelKey`) sat three lines above it in the same file. Fixed by switching to a `FREQUENCY_LABEL_KEY` map resolved with `t()` at render. `scripts/check-frozen-i18n.ts` now fails the build on any recurrence.

## Found by code review during QA test-plan authoring (2026-08-29, fixed same session)

All three were found by reading `db/database.ts` while writing the production-readiness test plan — none were user-reported, and none were caught by the existing 153-test suite because each sits in a gap the automation structurally cannot reach (timezone-dependent SQL, a guard whose bypass only fires against real FK enforcement, and a missing schema constraint that the UI happens to shadow). Each now has a regression test. See [[2026-08-29b-session]].

- **Trends and the Dashboard bucketed months in different timezones** — `fetchCategoryTotals()` buckets with `strftime('%Y-%m', …, 'unixepoch', 'localtime')`, but `fetchMonthlyTotals()` (which feeds the Trends chart) omitted `'localtime'` and bucketed in UTC. The `'localtime'` modifier was added to the first function on 2026-07-27 precisely to fix this class of bug; the second function was missed. Effect: in any non-UTC timezone, a transaction logged near a month boundary lands in a different month on Trends than on the Dashboard, so the two screens disagree. Fixed by adding `'localtime'` to both `strftime` calls in the query (`db/database.ts`), which also aligns the SQL with the local-time `monthKeys` the same function builds in JS. **Test:** new case in `db/__tests__/database.test.ts` asserts the Trends bucket equals `fetchCategoryTotals()` for the same month key, using instants at both edges of the current local month. Note the unit test can only fail when the runner's timezone is not UTC — CI runs in UTC — so the real proof is the manual on-device case `T-TZ-01` in the test plan.
- **`deleteAccount()` didn't count transfers, so the guard could be bypassed into a foreign-key error** — the reference check counted rows in `transactions` and `recurring` only. An account referenced *solely* by a row in `transfers` passed the guard, and the subsequent `DELETE` then hit `transfers.from_account`/`to_account REFERENCES accounts(id)` with `PRAGMA foreign_keys = ON`, surfacing as a raw SQLite exception instead of the polite "account in use" return of `false`. Fixed by adding a third count over `transfers` (either side) to the same guard. **Test:** new case asserts `deleteAccount()` resolves `false` for both the source and the destination account of a transfer, and that neither is removed.
- **`goals.target_amount` had no positive constraint** — it is the only money column in the schema without one (`transactions.amount`, `budget_limits.amount`, `category_balance.amount` and `transfers.amount` all carry `CHECK(… > 0)` or `>= 0`). A non-positive target reaching the DB divides by zero in the shared `ProgressBar` fill maths. In practice `GoalsModal.tsx` already validated `target <= 0` and both `BentoCard`/`GoalsModal` guard the ratio at render, so this was latent rather than reproducible through the UI — the exposure was any future caller of `insertGoal`/`updateGoal`. Fixed with an `assertPositiveTarget()` guard in `db/database.ts` that throws the same shape of message a `CHECK` violation would, rather than a v9 table-rebuild migration: adding a real `CHECK` to SQLite requires recreating the table, and `goals` is referenced by `transactions.goal_id` under `foreign_keys = ON`, which makes the rebuild materially riskier than the defect. **Test:** new case asserts insert and update both reject `0`, a negative and `NaN`, and that a rejected update leaves the stored goal unchanged.
