## What was done

### 1. Production-readiness test plan (deliverable)

Published as an artifact: **ChronoBudget Release Test Plan** — <https://claude.ai/code/artifact/713ca170-f7ad-4a6c-866e-8a7458554617>

190 cases across 20 suites, each with preconditions, numbered steps, an expected result and a P0/P1/P2 priority. Fifteen functional suites (`ON`, `DASH`, `FAST`, `DET`, `EDIT`, `HIST`, `TRD`, `LIM`, `BAL`, `REC`, `ACC`, `GOAL`, `SMART`, `I18N`, `SET`) and eleven technical ones (`T-DB`, `T-TZ`, `T-PERF`, `T-PLAT`, `T-LIFE`, `T-FILE`, `T-SEC`, `T-A11Y`, `T-BUILD`, `T-ERR`, `T-WEB`). The page carries a search/priority filter and per-case pass/fail/N-A tracking in `localStorage` so it doubles as an execution sheet.

The technical half was scoped from a deliberate coverage read: the Jest DB suite runs against a `sql.js` stand-in on fresh in-memory databases, and Playwright drives the web build, which uses `:memory:`. So nothing in CI today exercises native WAL persistence, the upgrade migration ladder against a real device file, foreign-key enforcement, native file I/O, or anything time- or device-dependent. The plan opens with a table of what *is* already automated so testers don't duplicate CI.

Also captured in the plan, as decisions to make rather than results to assert: CSV re-import silently doubles data (no de-duplication in `insertTransactionsBulk`); Android auto-backup may upload the SQLite file to Google Drive, which would contradict the published "data never leaves your device" claim; there is no error boundary and no crash reporter, so production failures are invisible; and `supportsTablet: true` ships an iPad layout nobody has reviewed.

### 2. Three defects fixed

All three are written up in full in [[open-issues]] under "Found by code review during QA test-plan authoring". In brief:

- `fetchMonthlyTotals()` bucketed months in UTC while `fetchCategoryTotals()` bucketed in local time — Trends and the Dashboard disagreed near month boundaries outside UTC. Added `'localtime'` to both `strftime` calls.
- `deleteAccount()` counted references in `transactions` and `recurring` but not `transfers`, so an account referenced only by a transfer bypassed the guard and hit the foreign key inside SQLite. Added a third count over `transfers`.
- `goals.target_amount` was the only money column with no positive constraint. Added an `assertPositiveTarget()` guard in the DB layer.

Three regression tests added to `db/__tests__/database.test.ts`.

## Decisions made

- **Guard `goals.target_amount` in application code rather than with a v9 migration.** Adding a real `CHECK` to SQLite means recreating the table, and `goals` is referenced by `transactions.goal_id` under `PRAGMA foreign_keys = ON`. The rebuild is materially riskier than the latent defect it would close, and the codebase already has precedent for DB-layer guards (`learnKeyword` early-returns on an empty key; `setLimit`/`setBalance` handle `amount <= 0` in the helper rather than the UI). The guard throws a `CHECK constraint failed: goals.target_amount` message so the failure reads the same as its sibling columns. Recorded as an addendum to [[savings-goals-schema]].
- **Accept that the timezone regression test cannot fail in CI.** The unit test asserts the invariant (Trends bucket equals the Dashboard total for the same month key) at both edges of the current local month, but CI runs on `ubuntu-latest` in UTC, where local and UTC bucketing are identical by definition. The on-device proof is manual case `T-TZ-01`, run at UTC−8 and UTC+13. Documented in the test's own comment so nobody later reads a green CI job as coverage of this.
- **No new ADR for the other two fixes** — both are corrections to existing documented behaviour, logged in [[open-issues]] and as an addendum to [[account-aware-budgeting]].
