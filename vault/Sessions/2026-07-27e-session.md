# Session — 2026-07-27 (later)

## Summary

Follow-up to [[2026-07-27d-session]], which flagged three items as out of scope for the initial account-aware-budgeting pass. Picked up two of the three (confirmed with the user): the account picker in `RecurringModal.tsx`, and a read-only accounts-balance row on the Dashboard. Generic bank-CSV import (the third flagged item) stayed explicitly out of scope.

## What was done

### Part 1 — Account picker in RecurringModal
- `db/database.ts`: `fetchRecurring()` now selects `account_id AS accountId`; `insertRecurring()`/`updateRecurring()` gained an optional `accountId` field, written through to the `recurring` table's `account_id` column. `processRecurring()`'s posting loop now includes `account_id` in every `INSERT INTO transactions` it runs for a due occurrence, and applies `UPDATE accounts SET balance = balance - ?` for that occurrence's amount when the rule carries an account — same atomic pattern as `insertTransaction`, still inside the existing `withTransactionAsync` block so multi-occurrence catch-ups (e.g. 4 missed months) debit the account once per occurrence, atomically.
- `store/useBudgetStore.ts`: `RecurringRule` gained `accountId?: number | null`.
- `components/RecurringModal.tsx`: added the same "None + one chip per account" picker `ExpenseInput.tsx`/`EditTransactionModal.tsx` already had (reusing the file's existing `subChip`/`subLabel` styles, no new style objects needed), placed after the note field and before the frequency pills. `accountId` state resets in `resetForm()`, prefills from `rule.accountId ?? null` in `openEdit()`, and is included in the `fields` object passed to both `insertRecurring`/`updateRecurring`.
- `components/__tests__/RecurringModal.test.tsx`: two exact-match `toHaveBeenCalledWith({...})` assertions (add flow, edit flow) needed `accountId: null` added — same fix pattern as `ExpenseInput.test.tsx`/`EditTransactionModal.test.tsx` broke and were fixed in the prior session.
- New tests in `db/__tests__/database.test.ts`: a `processRecurring` case asserting a tagged account's balance is debited once per posted occurrence (4 catch-up occurrences → 4× debit), plus an `accountId` round-trip case (insert → fetch → update → fetch) and a default-to-null case.

### Part 2 — Dashboard accounts summary
- `app/(tabs)/index.tsx`: `DashboardHeader` gained an `onOpenAccounts` prop and an `accounts` store subscription. A horizontal `ScrollView` row of small read-only account cards (bank icon + name + `formatCurrency(balance)`, negative balances in the same `#FF2D78` used elsewhere for over-limit/negative states) was added between the Needs/Wants/Savings `BentoCard` grid and the "RECENT" section label — rendered only when `accounts.length > 0`, so it's invisible to anyone who hasn't set up an account. Tapping a card opens `AccountsModal` (already existed from the prior session, just not reachable from the Dashboard before). Wired at the screen level exactly like the existing `limitsOpen`/`settingsOpen`/`recurringOpen` state + modal-render pattern (new `accountsOpen` state, `<AccountsModal visible={accountsOpen} onClose={...} />`).
- Kept inline inside `DashboardHeader` rather than extracted into its own component file — it's used in exactly one place, consistent with the codebase's low-abstraction preference (mirrors how the `BENTO_CONFIG` grid itself is inlined).
- No new DB fetch wiring needed — `accounts` was already loaded into the store on every `refreshCounter`/`dbReady` change since the prior session's Phase 3 work.

Not a surprise (anticipated in the plan before implementation), fixed by adding `accountId: null` to both expected objects.

Re-testing it here would not have been a good use of the same broken tooling, so verification relied on `tsc`/`npm test`/code review plus a basic no-error page-load smoke check instead.
