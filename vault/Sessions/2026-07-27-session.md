**Implementation 1 — month-scoped dashboard totals.**
- Added `currentMonthKey()` helper and gave `fetchCategoryTotals()` an optional `monthKey` param (defaults to current month; `null` for all-time).
- Found and fixed a timezone bug in the process: SQLite's `strftime(..., 'unixepoch')` computes the month boundary in UTC, but JS's `getFullYear()/getMonth()` are local-time — they silently disagree near midnight in non-UTC zones. Added the `'localtime'` SQL modifier so both sides use the same clock.
- Changed the header label from "Total Spent" to "Spent This Month" to match the new semantics.
- Updated `db/__tests__/database.test.ts`: the `processRecurring` catch-up test now explicitly passes `fetchCategoryTotals(null)` (it intentionally spans multiple months); added a new test proving the current-month default excludes a prior month.

**Implementation 2 — recurring custom start date.** Ran a second scoping pass specifically for date-picker UI (no library or pattern existed anywhere in the codebase — confirmed via full grep of `package.json` and components/app), then a Plan agent to design the approach; confirmed with the user that past start dates should be allowed and immediately catch up (rather than disallowed/clamped).
- `insertRecurring()` (`db/database.ts`) gained an optional `startDate` param that seeds `next_run` directly; no schema change.
- New `components/DatePickerField.tsx`: a self-contained single-month grid picker (prev/next navigation, day cells, "Today" quick-reset), modeled on the onboarding country picker's bordered-panel pattern rather than adding `@react-native-community/datetimepicker` (no web support, would need `Platform.OS` branching, and CLAUDE.md says avoid unnecessary libraries).

## Decisions made

- Reused `next_run` as the sole anchor/due-date field for recurring rules rather than adding a `start_date` column.
- Fixed the underlying UTC/local-time inconsistency (`'localtime'` SQL modifier) rather than switching `currentMonthKey()` to UTC getters — matches the user's device calendar month, which is what "this month" should mean for a budgeting app.
- Custom start date is create-only, not editable on existing rules — avoids the harder question of what changing an anchor mid-life means for an active rule.
- Past start dates are allowed and immediately trigger catch-up postings (user's explicit choice over disallowing/clamping) — reuses `processRecurring`'s existing due-occurrence loop with zero special-casing, consistent with how a brand-new rule already posts immediately today.
- Hand-rolled the date picker instead of adding a library, per CLAUDE.md's "avoid unnecessary libraries" and to sidestep `@react-native-community/datetimepicker`'s lack of web support.
- Split the e2e fix and the recurring-date feature into two separate commits rather than one, since they were unrelated changes (a regression fix vs. a new feature) — keeps history bisectable.

## Problems encountered

- The new month-scoped totals test initially failed — root cause was the UTC-vs-local timezone mismatch described above (local dev machine is UTC+2). Confirmed via `node -e` that `new Date(2026,6,1)` is `2026-06-30T22:00:00Z`, i.e. June in UTC but July locally. Fixed by adding `'localtime'` to the SQL.
- Browser-preview verification of the onboarding/tutorial overlays: synthetic `click`/`PointerEvent` dispatch didn't register on the overlay's own buttons in this environment, and coordinate-based clicks were off due to a viewport/screenshot-space scale mismatch (1280×720 vs the page's actual 800×450). Worked around both times by driving the underlying dashboard elements directly via `dispatchEvent` (bypasses overlay hit-testing) — confirmed real end-to-end behavior both sessions.
- While testing the date picker, dispatching two clicks (next-month + day-tap) back-to-back in one script executed before React's batched state update flushed, producing a stale-closure day pick ("Jul 20" instead of "Aug 20"). Not an app bug — splitting into two separate tool calls (one render cycle apart) picked the correct date. Worth remembering for future browser-tool verification: don't chain multiple state-changing dispatches in a single script without a yield/render gap.
- The `gh` CLI wasn't available in this environment (neither Bash nor PowerShell), so checking CI status required going directly to the GitHub REST API (`api.github.com/repos/.../actions/runs`, then `.../jobs`) via `WebFetch`; the job log's raw-log endpoint (`/actions/jobs/{id}/logs`) returned 403 even for this public repo, so the human-readable job page (`github.com/.../actions/runs/{id}/job/{id}`) was used instead to read the failure details.
