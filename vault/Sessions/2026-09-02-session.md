## Part 4: Savings transactions gain a Deposit/Withdrawal direction

User raised a conceptual gap, not a bug report: "usually the need is for the user to add money to savings... when the user inputs an amount for saving, does it need to be added to savings or removed?" Investigation confirmed the app had no concept of a savings withdrawal at all — `transactions.amount` was always positive with no sign, so every Savings-category transaction unconditionally added to the monthly total and (if tagged) a goal's `current_amount`. There was no way to record taking money out of savings (e.g. using the "Car repair fund" to pay for the real repair).

Used `AskUserQuestion` twice to scope this before planning: (1) add a Deposit/Withdrawal toggle (chosen, over a wording-only fix that would've left the gap unsolved) and (2) keep a withdrawal standalone — it just reduces the Savings total/goal progress on its own, not linked to a Needs/Wants entry (chosen, over a bigger "linked transfer" feature).

### What was done
1. **Schema migration v9**: `transactions.kind TEXT NOT NULL DEFAULT 'deposit'`, no `CHECK` (consistent with this project's established ALTER-vs-CHECK precedent — see the new addendum in [[savings-goals-schema]]). New `TransactionKind` type in `store/useBudgetStore.ts`.
2. **The key correctness detail**: `db/database.ts`'s `insertTransaction`/`updateTransaction`/`deleteTransaction` now compute a signed `delta` (`kind === 'withdrawal' ? -amount : amount`) and apply it to *both* a tagged goal's `current_amount` **and** a tagged account's `balance` — a withdrawal credits the account instead of debiting it, since the money is coming back out of the abstract savings bucket. Easy to miss if only the goal math got patched.
3. `fetchCategoryTotals`/`fetchMonthlyTotals` now net deposits and withdrawals via a `SUM(CASE WHEN kind = 'withdrawal' THEN -amount ELSE amount END)` — a no-op for Needs/Wants. Nothing downstream (BentoCard, the detail sheet, Trends) needed to change.
4. **UI**: `ExpenseInput.tsx`/`EditTransactionModal.tsx` gained a small Deposit/Withdrawal chip toggle, shown only for Savings (same conditional pattern the goal-chip picker already used), reset to Deposit whenever the category leaves Savings.
5. **Visibility fix**: without a visual cue, a withdrawal row looks identical to a deposit row in History/Recent. New `formatSignedAmount()` (`lib/format.ts`) prefixes a withdrawal's amount with `-`, used in both `TransactionRow` (`app/(tabs)/index.tsx`) and `HistoryRow` (`app/(tabs)/history.tsx`).
6. New i18n keys `input.deposit`/`input.withdrawal` (en/fr).

### Explicitly out of scope (documented in [[savings-goals-schema]])
CSV round-trip doesn't carry `kind` (same accepted gap as account/goal tags); recurring rules stay deposit-only; no floor preventing over-withdrawal (matches existing account-balance precedent); the Savings card's "OVER limit" framing is still backwards for a category where saving more is good — pre-existing, not touched, flagged as a follow-up.

### Testing
Extensive new coverage in `db/__tests__/database.test.ts` (signed-delta math for goal + account on insert/update/delete, totals netting, default-kind backward compatibility), `lib/__tests__/format.test.ts` (`formatSignedAmount`), and `components/__tests__/ExpenseInput.test.tsx`/`EditTransactionModal.test.tsx` (toggle visibility, submission, reset-on-category-change). Two pre-existing schema-version assertions bumped from 8 to 9. `tsc --noEmit`, `npm run check`, `npm test` — all clean, **228/228** tests passing. No browser/manual testing — user verifying on-device, per this session's established preference.

## Part 5: two corrections to the deposit/withdrawal feature, same day

User tested Part 4's feature and found two real problems, described as an "expert UI/UX + very naggy end user" review:

1. **Fast mode silently defaulted every Savings entry to Deposit** — the toggle only lived inside the collapsed override panel, invisible unless deliberately opened.
2. **Limit/Balance reacted to the net total, not withdrawals** — depositing (growing savings, good) could trigger the red OVER badge; withdrawing could silently clear it. Backwards. This was the exact "OVER limit framing is backwards for savings" issue flagged as an out-of-scope follow-up in Part 4 — turned out to be a real calculation bug, not just an unfortunate label.

Used `AskUserQuestion` twice to scope the fix: inline preview chip (over an auto-expanding panel or a submit confirmation step) for Fast mode, and a Deposited/Withdrawn breakdown in the detail sheet — user's own words: "the saving should reflect how much was saved and how much was used, both are needed."

### What was done
1. New `fetchSavingsWithdrawn()` (`db/database.ts`), mirroring `fetchCategoryTotals`'s month-scoping, scoped to `kind = 'withdrawal'`.
2. `BentoCard`/`BentoCardDetailModal` gained an optional `consumption?: number` prop driving all Limit/Balance math instead of `amount` — defaults to `amount` when omitted, so Needs/Wants and every prior test stayed unaffected. `app/(tabs)/index.tsx` fetches `savingsWithdrawn` and threads it through as `consumption` for the Savings card/modal only.
3. Detail sheet: when `consumption` is provided, "Spent This Month" is replaced with **Net saved this month** / **Deposited** / **Withdrawn** rows (`Deposited` derived as `amount + consumption`, no extra query). New i18n keys `card.netSaved`/`card.deposited`/`card.withdrawn`.
4. Fast mode: `ExpenseInput.tsx`'s preview row gained an inline Deposit/Withdrawal chip (shown only for Savings), tappable to flip instantly without opening the override panel. Removed the now-redundant copy of the toggle from the panel's own Fast-mode block. Clearing the field mid-typing now also resets `kind` to deposit.

Full rationale recorded in [[savings-goals-schema]]'s new addendum.

### Testing
New coverage in `db/__tests__/database.test.ts` (`fetchSavingsWithdrawn`), `components/__tests__/BentoCard.test.tsx` + `BentoCardDetailModal.test.tsx` (`consumption` prop proving a deposit-heavy net amount doesn't trip the limit/balance while a withdrawal does, breakdown rows), and `components/__tests__/ExpenseInput.test.tsx` (inline chip hidden until Savings, flips on tap, submits the right `kind`, absent in Detailed mode). `tsc --noEmit`, `npm run check`, `npm test` — all clean, **242/242** passing.
