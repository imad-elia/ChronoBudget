## Part 4: Savings transactions gain a Deposit/Withdrawal direction

User raised a conceptual gap, not a bug report: "usually the need is for the user to add money to savings... when the user inputs an amount for saving, does it need to be added to savings or removed?" Investigation confirmed the app had no concept of a savings withdrawal at all — `transactions.amount` was always positive with no sign, so every Savings-category transaction unconditionally added to the monthly total and (if tagged) a goal's `current_amount`. There was no way to record taking money out of savings (e.g. using the "Car repair fund" to pay for the real repair).

Used `AskUserQuestion` twice to scope this before planning: (1) add a Deposit/Withdrawal toggle (chosen, over a wording-only fix that would've left the gap unsolved) and (2) keep a withdrawal standalone — it just reduces the Savings total/goal progress on its own, not linked to a Needs/Wants entry (chosen, over a bigger "linked transfer" feature).

### What was done
1. **Schema migration v9**: `transactions.kind TEXT NOT NULL DEFAULT 'deposit'`, no `CHECK` (consistent with this project's established ALTER-vs-CHECK precedent — see the new addendum in [[savings-goals-schema]]). New `TransactionKind` type in `store/useBudgetStore.ts`.
2. **The key correctness detail**: `db/database.ts`'s `insertTransaction`/`updateTransaction`/`deleteTransaction` now compute a signed `delta` (`kind === 'withdrawal' ? -amount : amount`) and apply it to *both* a tagged goal's `current_amount` **and** a tagged account's `balance` — a withdrawal credits the account instead of debiting it, since the money is coming back out of the abstract savings bucket. Easy to miss if only the goal math got patched.
3. `fetchCategoryTotals`/`fetchMonthlyTotals` now net deposits and withdrawals via a `SUM(CASE WHEN kind = 'withdrawal' THEN -amount ELSE amount END)` — a no-op for Needs/Wants. Nothing downstream (BentoCard, the detail sheet, Trends) needed to change.
4. **UI**: `ExpenseInput.tsx`/`EditTransactionModal.tsx` gained a small Deposit/Withdrawal chip toggle, shown only for Savings (same conditional pattern the goal-chip picker already used), reset to Deposit whenever the category leaves Savings.
5. **Visibility fix**: without a visual cue, a withdrawal row looks identical to a deposit row in History/Recent. New `formatSignedAmount()` (`lib/format.ts`) prefixes a withdrawal's amount with `-`, used in both `TransactionRow` (`app/(tabs)/index.tsx`) and `HistoryRow` (`app/(tabs)/history.tsx`).
6. New i18n keys `input.deposit`/`input.withdrawal` (en/fr).

### Explicitly out of scope (documented in [[savings-goals-schema]])
CSV round-trip doesn't carry `kind` (same accepted gap as account/goal tags); recurring rules stay deposit-only; no floor preventing over-withdrawal (matches existing account-balance precedent); the Savings card's "OVER limit" framing is still backwards for a category where saving more is good — pre-existing, not touched, flagged as a follow-up.

### Testing
Extensive new coverage in `db/__tests__/database.test.ts` (signed-delta math for goal + account on insert/update/delete, totals netting, default-kind backward compatibility), `lib/__tests__/format.test.ts` (`formatSignedAmount`), and `components/__tests__/ExpenseInput.test.tsx`/`EditTransactionModal.test.tsx` (toggle visibility, submission, reset-on-category-change). Two pre-existing schema-version assertions bumped from 8 to 9. `tsc --noEmit`, `npm run check`, `npm test` — all clean, **228/228** tests passing. No browser/manual testing — user verifying on-device, per this session's established preference.

## Part 8: Trends gets a time-range picker

User reported Trends was stuck at the last 6 months and asked for a picker: 1 month, 3 months, 6 months, 1 year, 3 years, 5 years, and all-time. Investigation found `fetchMonthlyTotals` was already generic to an arbitrary N (existing tests already called it with `3` and `1`) — the two real gaps were an "all-time" mode (no existing concept of "however many months of history exist") and the hand-rolled bar chart's fixed-width bars, which would overflow at 36-60+ bars with no scroll handling. Used `AskUserQuestion` to settle the long-range chart question: horizontal scroll while staying strictly monthly at every range (chosen), over auto-switching to quarterly/yearly buckets for long ranges (bigger change, and "one bar = one month" would stop being true).

### What was done
1. `db/database.ts`'s `fetchMonthlyTotals(months = 6)` → `fetchMonthlyTotals(range: number | 'all' = 6)`. Numeric behavior byte-for-byte unchanged (same loop, same query, same zero-fill). `'all'` queries `MIN(timestamp)` and anchors the month range to the earliest transaction's local month (same local-time `Date`-accessor convention as the rest of the function, no UTC) through the current month; `[]` when there are no transactions at all.
2. `app/(tabs)/trends.tsx`: new `RANGE_OPTIONS` config (7 entries: 1m/3m/6m/1y/3y/5y/all) rendered as a horizontally-scrollable chip row under the header, visually matching `history.tsx`'s `filterChip` treatment (colored border + tint when active) but auto-width instead of `flex:1`, since 7 options don't fit evenly on a phone the way History's 4 do. Selection persists via `getSetting`/`setSetting('trends_range', ...)`, the same pattern `ExpenseInput.tsx` already uses for `input_mode`; defaults to `6m` (today's behavior) with nothing persisted. The previously-static subtitle ("Last 6 months", wrong for every other range) is now range-driven off each option's own `subtitleKey`.
3. `MonthlyChart`'s bar row moved inside a horizontal `ScrollView`; `monthGroup` kept its `flex: 1` and gained a `minWidth: 34` floor — a standard flex trick needing no width math in JS: short ranges (≤6 months) still fill the row edge-to-edge exactly as before (their total minWidth is under the container width), while longer ranges exceed it and the row becomes scrollable with bars held at the `minWidth` floor instead of being squeezed illegibly thin.

### Testing
New `db/__tests__/database.test.ts` cases: `fetchMonthlyTotals('all')` returns `[]` on an empty DB, and correctly spans from an inserted transaction's month through the current month (zero-filling the gap) on a populated one. `tsc --noEmit`, `npm run check`, `npm test` — all clean, **251/251** passing.

Browser-verified end-to-end on the running Expo web dev server (already up on `:8081` from an earlier session): default 6M unchanged from before, 5Y renders 60 bars and scrolls horizontally correctly (verified by scrolling and watching the month-label axis advance), 1Y comfortably fits without scrolling, and "All" correctly showed exactly one bar (the only month with data) rather than a fixed 6/12/etc. A full page reload reset both the data and the persisted range back to 6M/empty — expected, matches the already-documented web in-memory-DB limitation ([[web-inmemory-db]]), not a bug in this feature; persistence would survive on native (persisted SQLite).

Committed and pushed as [a14c2e3](https://github.com/imad-elia/ChronoBudget/commit/a14c2e3).

## Part 9: Trends redesigned — adaptive granularity + tap-to-drill (same-day reversal of Part 8's chart choice)

User tried Part 8's range picker and found the real flaw with its "stay monthly + horizontal scroll" chart: at 3Y/5Y/All the same `Jan`/`Feb`/`Mar`… labels repeat once per year with no way to tell which year, and scrolling through up to 60 near-identical bars is poor UX. Asked, as a UI/UX expert, for a genuine redesign rather than a label patch. Used `AskUserQuestion` to confirm the direction — **adaptive granularity** (bar granularity changes with the selected range: month → quarter → year, so every range fits on screen with no ambiguity and no scrolling) over the smaller alternative of just adding year markers to the existing monthly-scroll chart. The user's own follow-up in that same answer asked whether tap-to-drill was possible, which became part of the design.

### What was done
1. **`db/database.ts`**: two new functions mirroring `fetchMonthlyTotals`'s established pattern — `fetchQuarterlyTotals(quarters = 12)` (`QuarterlyTotal { quarter: 'YYYY-Q1', ... }`, quarter bucket computed in SQL from year + `((month-1)/3+1)`) and `fetchYearlyTotals(range: number | 'all' = 5)` (`YearlyTotal { year: 'YYYY', ... }`, `'all'` anchored to `MIN(timestamp)`'s year same as `fetchMonthlyTotals('all')`). `fetchMonthlyTotals` gained a third range shape, `{ startMonth, endMonth }` — an explicit inclusive window unrelated to "now", powering drill-down; required generalizing its WHERE clause from open-ended `>=` to `BETWEEN`, a no-op for the two existing shapes but necessary for a window that doesn't end at the current month.
2. **`app/(tabs)/trends.tsx`**: `RANGE_OPTIONS` gained a `granularity` field — 1M-1Y stay monthly (unchanged), 3Y renders 12 quarterly bars, 5Y/All render yearly bars. Tapping a year or quarter bar drills one level into its months (via the new `{ startMonth, endMonth }` shape), with a small "‹ 2023"-style back pill replacing the subtitle while drilled in; switching range chips always clears the drill. Drill state is intentionally not persisted (unlike `range`).
3. The chart component (renamed `MonthlyChart` → `TrendsChart`) now draws from a normalized `ChartBar { key, label, needs, wants, savings }` shape instead of being hard-wired to `MonthlyTotal` — each fetch result maps into it before rendering, with only label formatting differing per granularity (month/quarter/year). The bar-drawing/scaling/horizontal-scroll code from Part 8 is unchanged and entirely granularity-agnostic; an optional `onBarPress` prop drives the new drill interaction.
4. Quarter labels are locale-aware ("Q1 '24" in English, "T1 '24" in French — the French convention is "trimestre") via the existing `getActiveLocale()`. No new i18n dictionary keys needed — the back-pill label is just a chevron plus numbers.

Full rationale, including why the Part 8 approach was reverted, in the new [[Decisions/trends-adaptive-granularity]].

### Testing
New `db/__tests__/database.test.ts` cases for `fetchQuarterlyTotals`, `fetchYearlyTotals` (numeric + `'all'`), and the `{ startMonth, endMonth }` shape (including a case proving the window is bounded on both ends, not open-ended). `tsc --noEmit`, `npm run check`, `npm test` — all clean, **257/257** passing.

Browser-verified end-to-end: 6M/1Y render exactly as before (unchanged monthly view, no drill affordance on month bars — confirmed a tap is a no-op); 3Y renders 12 quarterly bars, scrolled to find the current quarter and tapped it — drilled correctly into its 3 months with the right data and a working "‹ Q3 2026" back pill; 5Y renders exactly 5 yearly bars with no scrolling needed, tapped the current year and it drilled into its 12 months correctly with a "‹ 2026" back pill; switching to a different range chip while drilled in correctly cleared the drill. No console errors.

## Decisions made
- Balance-badge wording split (`card.overby` vs `card.over`) — user's own manual edit, reviewed and confirmed correct (Part 1).
- Large-amount overflow fix: compact text + tap-to-expand detail sheet, chosen over tap-only/compact-only/responsive-stacked alternatives (Part 2). Compact threshold later lowered from $10K to $1K (Part 3).

- Trends' long-range chart initially stayed strictly monthly with horizontal scroll, rather than auto-aggregating to quarterly/yearly buckets for readability (Part 8) — **reversed the same day** once real usage showed the year-ambiguity flaw; replaced with adaptive granularity (month/quarter/year based on range) plus one-level tap-to-drill (Part 9).
