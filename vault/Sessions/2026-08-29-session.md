## Part 4: Fast mode was discarding the typed description

User report: typing "10 coffee" correctly detected Wants · Dining, but "coffee" itself disappeared — not saved anywhere. Investigated: the classifier (`lib/detectCategory.ts`) never actually strips or mutates the description; the bug was one line downstream in `components/ExpenseInput.tsx`'s `handleSubmit`, which unconditionally passed `''` as the note for Fast-mode submissions (`mode === 'detailed' ? note : ''`). Fixed by passing `description` (the already-computed leftover text after the amount is parsed out) instead of `''`, so the full leftover phrase (e.g. "coffee", or "morning coffee run" for multi-word input) is now saved as the transaction's note. No DB/schema change needed. Updated `components/__tests__/ExpenseInput.test.tsx`'s `"15 coffee"` submit assertion (note `''` → `'coffee'`). Verified via `tsc --noEmit` + `npm test` (261/261). See [[smart-input-classifier]].

## Part 5: tour card jumped position between steps

User report: the tour popup changed vertical position every time Next was tapped. Root cause: Welcome/Budget Limits steps centered the card vertically while Fast Mode/Detailed Mode steps pinned it by the bottom edge 220px from the screen bottom (with a small decorative pointer arrow), growing upward as content got taller — two incompatible positioning rules switching every step. Fixed by using one rule for all 4 steps: pin the card's top edge at a fixed proportion of screen height (`top: windowHeight * 0.16`) via the existing `useWindowDimensions()` hook, so height stays auto and a longer step just extends further down instead of moving. Removed the now-pointless pointer arrow and the `anchorFromBottom` field. Scoped strictly to the tour phase, not the country/balance screens. Verified via `tsc --noEmit` + `npm test` (261/261). See [[localization]].

## Part 7: manual override stuck across unrelated entries

User report: override "15 coffee" to Needs · Groceries, clear the field, type "15 coffee" again — stayed on Needs · Groceries instead of re-detecting Wants · Dining. Root cause: `overridden` in `ExpenseInput.tsx` is a plain boolean with no per-entry scope, and only ever reset to `false` after a full submit (`resetFields()`) — never when the user simply cleared the field to start a new entry without submitting. Fixed by resetting `overridden`/`showOverride` in the smart field's `onChangeText` whenever it's cleared back to empty — a natural "new entry" signal, distinct from continuing to edit/refine the current one (which still correctly respects the override). Added a regression test in `components/__tests__/ExpenseInput.test.tsx` covering override → clear → retype → re-detect. Confirms existing intent: only an explicit correction *at submit time* feeds the learning table; detection itself is meant to be per-entry and shouldn't need a submit just to "unstick." Verified via `tsc --noEmit` + `npm test` (262/262). See [[smart-input-classifier]].
