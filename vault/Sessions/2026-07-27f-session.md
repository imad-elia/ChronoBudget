# Session — 2026-07-27 (later still)

## Summary

Started as a "double-check the vault's next steps" request. Verified all three documented next-steps against the actual code (via an Explore agent): non-English keyword dictionaries beyond French are genuinely still the only open item; CSV round-trip scope is confirmed as documented; account-aware budgeting is actually *more* complete than documented (`AccountsModal.tsx` already has a full transfer UI, not just schema/functions — a doc correction, not a code gap).

Rather than just doing routine follow-up, the user asked for an enhancement proposal on top of the verification. Proposed several options grounded in the product principles; the user had no strong preference, so picked **savings goals / sinking funds** — the product principles explicitly call out "specific to sinking funds and irregular expenses," yet "Savings" was just a flat category with no way to earmark money toward a named goal. Implemented it end-to-end.

## What was done

### Schema + DB layer
- `db/database.ts`: schema bumped to **v8** — new `goals` table (`id, name, target_amount, current_amount, created_at`) plus a nullable `goal_id` FK on `transactions`. New `fetchGoals`/`insertGoal`/`updateGoal`/`deleteGoal` (delete refuses when referenced by a transaction, same convention as `deleteAccount`). `insertTransaction`/`updateTransaction`/`deleteTransaction` all adjust `goals.current_amount` atomically inside the existing `withTransactionAsync` block when a transaction carries a `goal_id` — same pattern already used for `accounts.balance`.
- `store/useBudgetStore.ts`: new `Goal` type + `goals`/`setGoals` state, mirroring `Account`/`setAccounts`. `Transaction` gained `goalId?: number | null`.

### Shared UI
- Extracted `progressColor()` + the progress-bar fill/track/over-badge JSX out of `BentoCard.tsx` into a new `components/ProgressBar.tsx`, since `BentoCard` is tightly coupled to the fixed Needs/Wants/Savings grid and wasn't a clean fit for an arbitrary-length goals list. `BentoCard` now renders `<ProgressBar>`; `GoalsModal`'s goal rows do too.
- New `components/GoalsModal.tsx`, modeled on `AccountsModal.tsx` but dropping the `transfer` view entirely (goals don't transfer between each other). List view shows name + current/target amounts + a `ProgressBar`; form view is name + target amount only — a goal's `current_amount` only grows through tagged transactions, no direct balance edit (keeps the "money actually moved" invariant). Reachable from `SettingsModal.tsx` via a new "Goals" row, same pattern as the existing Accounts entry.
- `ExpenseInput.tsx`/`EditTransactionModal.tsx`: added a goal-chip picker (same chip UI as the account picker), rendered only when the selected category is Savings and at least one goal exists. `goalId` resets to `null` whenever the category changes away from Savings. `insertTransaction`/`updateTransaction` calls now pass `goalId` (or `null` for non-Savings categories).
- Dashboard (`app/(tabs)/index.tsx`): `DashboardHeader` gained a goals-progress row (name + percent complete), mirroring the existing accounts-balance row, shown only when `goals.length > 0`, tapping opens `GoalsModal`.
- `constants/i18n/en.ts` + `fr.ts`: added `settings.goals`, `goals.*`, `input.goal`/`input.noGoal` keys.

### Tests
- `db/__tests__/database.test.ts`: new `describe('goals', ...)` block — insert/fetch, rename without touching balance, credit on tagged insert, reverse-and-reapply on tagged update, debit-back on delete, delete-blocked-when-referenced, delete-with-no-references. Updated the schema-migration test's expected version (7→8) and table list (added `goals`), and the migration-idempotency test's expected version.
- New `components/__tests__/GoalsModal.test.tsx` (8 cases: empty state, seeded progress rendering, add-flow validation + save, edit-flow prefill + save, delete + delete-blocked), modeled on `RecurringModal.test.tsx`'s structure since no `AccountsModal.test.tsx` exists to copy from.
- `store/__tests__/useBudgetStore.test.ts`: added a `setGoals` case alongside the other simple setters.
- Fixed two exact-match `toHaveBeenCalledWith` assertions broken by the new `goalId` param: `ExpenseInput.test.tsx` (`insertTransaction` positional args) and `EditTransactionModal.test.tsx` (`updateTransaction` fields object) — same breakage class already seen twice before with `accountId`.

## Decisions made

- New `vault/Decisions/savings-goals-schema.md` — dedicated `goals` entity table (following the `accounts` precedent) rather than extending `category_balance` or folding goals into `accounts`. Goals represent an earmarked *purpose* within Savings; accounts represent where money physically sits — conflating them would make an account's balance ambiguous.
- Recurring rules do **not** get goal tagging in this pass (v1) — judged a plausible future extension, not required now.
